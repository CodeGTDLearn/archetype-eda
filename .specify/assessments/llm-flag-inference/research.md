# Idea Research: Inferência LLM das flags do `mvn archetype:generate`

- **Slug**: llm-flag-inference
- **Created**: 2026-10-12
- **Evidence confidence (overall)**: medium

## Users & Demand

- O único usuário identificado é o próprio dono do projeto `archetype-v2-eda` (mantenedor único). A demanda é *stated* (declaração explícita em texto livre), não *observed* (sem telemetria, sem tickets, sem dados de uso). [ASSUMPTION] (confidence: medium)
- A dor declarada é tripla: (a) operacional — manter `bash_script/` (~28 scripts `.sh` totalizando milhares de linhas); (b) cognitiva — responder prompts repetitivos para cada geração; (c) arquitetural — o JSON contrato do módulo existe só implicitamente, espalhado entre prompts do terminal e flags ad-hoc. [source: mensagem do usuário na abertura desta sessão; `bash_script/script_core.sh` linhas 1–100] (confidence: high)
- A intenção estratégica de **eliminar pré-processamento em bash do projeto** já foi declarada em ciclo anterior. Cumprida parcialmente: `groovy-snippet-injection` migrou o compositor de `archetype-post-generate.groovy` para Groovy build-time; este assessment é o próximo passo. [source: `bash_script/script_core.sh` linhas 41–45 — comentário explícito registra a substituição; `.specify/assessments/groovy-snippet-injection/intake.md`] (confidence: high)

## Prior Art

- **Interno (mesmo projeto):** compositor Groovy `SnippetComposer.groovy` (build-time, `gmaven:2.1.1` na fase `process-resources`) já demonstrou que a substituição de bash por código Groovy nativo é viável neste mesmo archetype. Esse precedente é o modelo direto para a substituição de `bash_script/maven_command_line_archetype_generate.sh` + `general_functions.sh` + todos os `user_*_input.sh`. [source: `.specify/assessments/groovy-snippet-injection/decision.md`; `bash_script/script_core.sh` linhas 41–45] (confidence: high)
- **Interno (mesmo projeto):** os 9 perfis IT em `src/test/resources/projects/` (`basic`, `binding-default-only`, `binding-list-only`, `binding-map-only`, `binding-validated-only`, `full`, `json-contract`, `minimal`, `binding-mutable-only`, `defaults-only` — na verdade **10 perfis**) já exercitam o ciclo `mvn archetype:generate` com combinações reais de flags. Esse é o harness de regressão natural para validar que o mecanismo novo produz comandos equivalentes aos esperados. [source: enumeração direta de `src/test/resources/projects/` em 2026-10-12] (confidence: high)
- **Externo (Spring Initializr / JHipster):** ferramentas maduras que já oferecem geração de projeto Spring Boot sem prompt interativo, via API REST. Não são substitutas diretas para o `eda-archetype` (que tem 34 propriedades específicas, incluindo `mutable_binding_properties`, `validated_binding_properties`, `properties_filetype`, `absolute_path_jsonfile_contract`, entre outras fora do escopo de Initializr), mas validam que o *pattern* "config declarativa → projeto gerado sem prompt" é conhecido e adotado. [ASSUMPTION — sem fetch permitido pelo policy; baseado em conhecimento público] (confidence: medium)
- **Externo (Maven Archetype Plugin interativo):** o `mvn archetype:generate` original prompta o usuário para cada `requiredProperty` sem `defaultValue`. Isso é o "modo atual" que o mecanismo substitui. Já existe flag `--batch-mode` (usada no `bash_script/maven_command_line_archetype_generate.sh` linha 3) que suprime prompts, mas exige todas as `-D` na linha de comando — exatamente o que o mecanismo vai gerar. [source: `bash_script/maven_command_line_archetype_generate.sh` linha 3] (confidence: high)
- **Externo (cancelled — não é prior art):** Spring Boot CLI (`spring init`) tem subconjunto de Initializr mas não cobre propriedades customizadas como `mutable_binding_properties` ou `validated_binding_properties`. Não é alternativa viável para o caso. [ASSUMPTION — baseado em conhecimento público; sem fetch permitido] (confidence: low)

## Market & Context

- **Alternativa atual (mantida):** `bash_script/maven_command_line_archetype_generate.sh` + 14 `user_*_input.sh` + `general_functions.sh` + `script_core.sh` montam o comando `mvn archetype:generate --batch-mode` após prompts interativos. A linha de comando gerada é estritamente equivalente ao comando alvo do mecanismo novo. [source: `bash_script/maven_command_line_archetype_generate.sh` (55 linhas, monta a string completa); `bash_script/script_core.sh` linhas 79–98 (injeta os scripts de input na ordem certa)] (confidence: high)
- **Alternativa atual (parcialmente migrada):** `groovy-snippet-injection` já substituiu o compositor de `archetype-post-generate.groovy`. Isso confirma que o projeto já tem o caminho técnico (Groovy build-time) para reescrever outras partes do bash. [source: `.specify/assessments/groovy-snippet-injection/decision.md`; `bash_script/script_core.sh` linhas 41–45] (confidence: high)
- **Custo de não fazer nada:**
  - `bash_script/` continua crescendo a cada nova flag — o próprio `README.md` lista um ritual de 10 passos para adicionar uma nova `requiredProperty` (criar script de input, injetar em `script_core.sh`, montar `-D` em `maven_command_line_archetype_generate.sh`, criar `archetype.properties` no test, criar XML do descriptor, criar fileSet, criar variable e snippet Groovy, registrar fileSet/requiredProperty). [source: `README.md` linhas 1081–1414] (confidence: high)
  - A barreira para um novo contribuidor continua sendo a leitura completa de todos os scripts bash antes de entender o que cada flag faz. [ASSUMPTION] (confidence: medium)
  - Cada execução do `script_core.sh` hoje trava em `read -n 1 -s` quando um erro acontece (4 ocorrências em `create_archetype_metadata.sh` e `create_archetype_post_generate.sh`). Após `groovy-snippet-injection`, esse `read` em `create_archetype_post_generate.sh` é contornável; mas o `script_core.sh` em si permanece dependente de TTY. [source: `bash_script/create_archetype_metadata.sh` linhas 67, 77; `bash_script/create_archetype_post_generate.sh` linhas 66, 84] (confidence: high)

## Data & Constraints

- **34 `requiredProperty` declarations distribuídas em 17 arquivos XML** — confirmado por contagem direta via grep. Esse é o catálogo canônico de flags. Cada `<requiredProperty key="…">` traz `<defaultValue>` (pode estar vazio, que dispara prompt do Maven) e opcionalmente `<validationRegex>`. [source: `src/main/resources/META-INF/maven/archetype_metadata_properties/*.xml`; enumeração `grep -c "<requiredProperty key="` retornando **34 matches** em 2026-10-12] (confidence: high)
- **Composição do `archetype-metadata.xml`:** 17 entidades `<!ENTITY property-… SYSTEM …>` resolvidas para os 17 XMLs de propriedades + 9 entidades `<!ENTITY fileset-… SYSTEM …>` resolvidas para os XMLs de filesets. O descriptor principal não traz flags inline — toda flag é externalizada via XInclude. Isso simplifica a extração automática de flags pelo mecanismo novo. [source: `src/main/resources/META-INF/maven/archetype-metadata.xml` linhas 3–30] (confidence: high)
- **10 perfis IT** exercitam o ciclo `mvn archetype:generate` end-to-end via `mvn integration-test`. O harness usa o fixture `basic/archetype.properties` (entre outros) como entrada. Cada perfil roda `archetype-post-generate.groovy` sobre o projeto gerado. [source: enumeração de `src/test/resources/projects/` em 2026-10-12; `.specify/assessments/archetype-integration-tests/problem.md`] (confidence: high)
- **Tooling já disponível:**
  - `xml-maven-plugin:1.2.1` + `identity.xsl` — já é usado para `archetype-metadata.xml` na fase `generate-resources`. Pode ser reaproveitado para extrair `requiredProperty` (via XPath/identidade XSLT). [source: `pom.xml`; `.specify/assessments/groovy-snippet-injection/research.md` linha 15] (confidence: high)
  - `gmaven:2.1.1` + Groovy 4.0.28 — já é usado para o `SnippetComposer.groovy` na fase `process-resources`. Pode ser reaproveitado para o validador de flags do mecanismo novo. [source: `.specify/assessments/groovy-snippet-injection/decision.md`; `bash_script/script_core.sh` linhas 41–45] (confidence: high)
- **JSON contrato — formato arbitrário (decidido no intake):** o JSON é livre, com campos arbitrariamente obrigatórios (todo campo presente é obrigatório por padrão), podendo ter objetos aninhados ou não. Não há schema fixo — o exemplo dado (`Pessoa` com `address` aninhado + `contacts[]`) é ilustrativo, não prescritivo. Isso significa que o mecanismo novo **não pode assumir schema**: precisa tratar o JSON como `Map<String, Object>` e validar campo-a-campo contra o catálogo de flags. [source: `.specify/assessments/llm-flag-inference/intake.md` — Resolved Decisions] (confidence: high)
- **Cache por (descrição + JSON):** decidido no intake que entradas repetidas não disparam nova chamada à LLM. Isso exige uma chave de cache estável — provavelmente SHA-256 da concatenação ordenada `(descrição textual || canonical-JSON)`. Implementação trivial em Groovy/Java via `MessageDigest`. [source: `.specify/assessments/llm-flag-inference/intake.md` — Resolved Decisions] (confidence: high)

## Evidence Against the Idea

- **Alucinação de flags pela LLM:** a LLM pode inventar uma `requiredProperty` que não existe nos 17 XMLs. Sem validação determinística contra `archetype-metadata.xml`, o `mvn archetype:generate` falha em runtime com mensagem confusa. Mitigação: validador Groovy contra o catálogo (já disponível via reaproveitamento do `xml-maven-plugin`/`gmaven`). Risco residual se o validador for contornado. [ASSUMPTION — risco clássico de LLMs; mitigação já mapeada] (confidence: medium)
- **Alucinação de tipos:** uma flag pode ter `validationRegex` (ex.: `^(true|false)$`, `^(false|([1-3]))$`, `^([1-9][0-9]{3,4})$` para porta HTTP) e a LLM pode propor valor que casa no `type` mas falha no regex (ex.: `mutable_binding_properties=2`, que casa `number` mas fura `(false|[1-3])`). Mitigação: o validador precisa aplicar `validationRegex` antes de montar a linha. [source: `src/main/resources/META-INF/maven/archetype_metadata_properties/property-binding-properties.xml` linhas 71–73; `property-api-general.xml` linhas 11–14, 24–26] (confidence: high)
- **Custo de inferência por feature:** cada feature criada via spec-kit gera 1 chamada à LLM. O usuário aceitou esse custo no intake, mas não fixou limite. Risco: se uma feature passar por múltiplas iterações de spec/plan/test, cada iteração pode disparar nova chamada. Mitigação parcial: o cache por (descrição + JSON) descrito acima. [ASSUMPTION] (confidence: low)
- **Não-determinismo:** LLMs produzem saídas estocásticas. Mesmo com cache, uma pequena mudança de temperatura pode gerar comandos diferentes para entradas equivalentes — o que viola o requisito implícito de reprodutibilidade do archetype. Mitigação: zerar temperatura (top_p=0) + cache. [ASSUMPTION] (confidence: medium)
- **Manutenção do validador:** o validador determinístico precisa ser mantido em sincronia com `archetype-metadata.xml`. Cada nova `requiredProperty` exige atualizar o validador? Não, se o validador extrai via XInclude/XML dinamicamente — basta reapontar para `src/main/resources/META-INF/maven/archetype_metadata_properties/`. Mas exige um teste do validador contra o XML atual para garantir que a extração não quebrou. [ASSUMPTION] (confidence: medium)
- **Integração com spec-kit é só textual:** como decidido no intake, não há ponto de injeção técnica — é só orientação nos templates `spec.md`/`plan.md`/`tasks.md` instruindo o operador a usar o mecanismo. Isso significa que o sucesso depende de o operador realmente usar a ferramenta, em vez de copiar/colar uma linha `mvn archetype:generate` antiga. [ASSUMPTION — comportamento humano] (confidence: low)
- **Sem URL confiável para pesquisar prior art externo:** a URL Trust Policy desta sessão restringe fetch a hosts específicos. `spring.io`, `maven.apache.org` direto, e `github.com` (repositórios do Spring Initializr / archetype-packaging) seriam úteis mas estão fora da allowlist exata. Não foi feito fetch — essa seção de prior art externo é baseada em conhecimento público pré-existente, marcado como tal. [ASSUMPTION] (confidence: low)

## Gaps & Open Questions

- [NEEDS CLARIFICATION: temperatura da LLM — o intake não fixou. Para reprodutibilidade byte-a-byte, sugere-se temperatura 0. Decidir em `/speckit.assess.define` ou `/speckit.specify`.]
- [NEEDS CLARIFICATION: granularidade da extração de flags — basta `<requiredProperty key="...">` ou também `<validationRegex>` e `<defaultValue>`? A LLM precisa do regex para validar o que propõe, e o defaultValue é a fonte de verdade para os defaults do archetype. Ambos provavelmente devem ser extraídos.]
- [NEEDS CLARIFICATION: quando a LLM e o JSON contrato discordam sobre uma mesma flag, qual sinal prevalece? O intake diz "contrato sempre vence" para o **valor**, mas e se a LLM propuser uma flag que o contrato não cita? Sugestão: a flag proposta pela LLM e ausente do contrato é descartada, a menos que seja default-obrigatória.]
- [NEEDS CLARIFICATION: como serializar o JSON contrato para a chave de cache — `ObjectMapper.writeValueAsString` (Jackson) garante ordem de campos? Se a ordem variar entre execuções, o hash muda e o cache erra. Decidir serialização canônica.]
- [NEEDS CLARIFICATION: o que fazer com flags que têm `<defaultValue></defaultValue>` (vazio) — sem default, o Maven prompta mesmo com `--batch-mode`. Essas flags são hoje responsabilidade do `user_*_input.sh` capturar o input antes de montar a linha. No mecanismo novo, a LLM deve inferir essas flags a partir da descrição textual (em vez de promptar o operador).]
